LLM Council Report — sinu-island-gateway Refactor

Generated: Thursday, 14 May 2026  |  5 advisors, 5 peer reviewers, 1 chairman  |  Topic: Package cleanup, dead code removal, file structure

Question: The sinu-island-gateway project is a combined React+TypeScript frontend (Vite/ShadCN/Tailwind) and Node.js/Express backend in a single monorepo, recently migrated from Mongoose/MongoDB to Prisma/PostgreSQL. Which packages should be removed (unused/redundant), which source files are dead code, and how should the remaining files be restructured correctly?

⚖ Council Verdict

Where the Council Agrees

  • Remove immediately (confirmed zero imports): styled-components, exceljs, @sanity/client, @sanity/image-url, vite-plugin-pwa, @types/axios, @types/dotenv, lovable-tagger.
  • The structural boundary problem is real: Backend files (src/app.ts, src/routes/, src/utils/, src/config/, src/lib/prisma.ts) coexist in the same src/ tree as Vite frontend files. This creates accidental-bundling risk.
  • Dead files are already deleted from disk (the 4 Mongoose model files) — only git rm staging remains.
  • connectDB runs a full-table backfill scan on every restart — a minor but real runtime overhead once all rows are migrated.

Where the Council Clashes

Scope of structural refactor: The Expansionist advocates a full npm workspaces split (frontend/ + server/). The Executor says just move files into a server/ directory without splitting package.json. The Executor is right for a live portal — npm workspaces restructuring is a separate day's work with its own deployment risk. Moving backend files to server/ is sufficient and safe.

Blind Spots the Council Caught

  • 🚨 CRITICAL: .env is tracked in git. All 5 peer reviewers independently identified this. The .env file containing live DATABASE_URL, JWT secrets, admin passwords, and SMTP credentials is committed to the repository. Credentials must be rotated and the file must be removed from git tracking before anything else.
  • Sanity CMS sub-project (/sanity/): Has its own package.json, but @sanity/client and @sanity/image-url are also in the root package.json — with zero imports in src/. Remove them from root deps; they belong only in sanity/package.json.

The Recommendation

Execute in three phases: (1) Security — remove .env from git tracking and rotate all credentials. (2) Cleanup — uninstall the 8 confirmed-unused packages, stage the 4 deleted model files. (3) Structure — move all backend files (src/app.ts, src/routes/, src/config/, src/utils/, src/types/, src/lib/prisma.ts) into a server/ directory at the project root, updating all imports and package.json scripts. Leave the Vite src/ tree as pure frontend. Do NOT split into npm workspaces yet — that's future work.

The One Thing to Do First

Add .env to .gitignore and run git rm --cached .env — then rotate all credentials in that file.

Full Advisor Responses

The Contrarian

Five verifiable risks in the codebase:

  1. connectDB backfill scan on every restart — dbconnect.ts queries all StudentApplication rows where phoneNormalized is null/empty on startup. After full migration this becomes a SELECT on the entire table on every server boot.
  2. exceljs installed but never imported — read-excel-file is the actual Excel parser. exceljs appears to be a leftover dependency from an earlier approach.
  3. @types/axios + @types/dotenv type pollution — axios v1+ and dotenv both ship their own types. Having @types/axios can cause type conflicts with the bundled types; @types/dotenv is deprecated.
  4. Sanity CMS sub-project orphaned in root deps — @sanity/client and @sanity/image-url are in the root package.json but have zero imports in src/. The Sanity project has its own package.json in /sanity/.
  5. "type": "commonjs" potential ESM conflict — The backend uses ESM-style import statements via ts-node/tsx. Having "type": "commonjs" in package.json may cause issues in some Node.js environments.
The First Principles Thinker

The question is not really "which packages to remove." The question is: why does this project have a structural boundary problem and what does fixing it actually require?

The root problem: src/lib/prisma.ts uses @prisma/client — a Node.js runtime package — but lives inside Vite's src/ tree. This is an architectural mistake. The same mistake was made with Mongoose (old model files in src/models/). Migrating to Prisma recreated the same error.

Remove (confirmed zero imports in src/): styled-components, @sanity/client, @sanity/image-url, @types/axios, @types/dotenv, lovable-tagger, vite-plugin-pwa.

The structural fix that matters: Create a server/ directory at the project root. Move all backend files there: app.ts, config/, routes/, utils/, types/, lib/prisma.ts. Keep only frontend files in src/.

The Expansionist

This cleanup is table stakes, not the opportunity. Consider:

  • PWA for Pacific Island users — vite-plugin-pwa is dormant but the Pacific Islands have unreliable connectivity. An offline-capable student portal would be transformative. Don't discard the package — implement it.
  • Excel import tooling as a moat — read-excel-file powering bulk programme/unit imports from admin spreadsheets is genuinely valuable. Invest in this; don't treat it as a liability.
  • npm workspaces opportunity — Splitting into frontend/ and server/ workspaces with separate package.json files enables independent deployments, cleaner CI/CD, and the ability to version them separately.
  • Prisma as platform foundation — Now that Prisma is in place, database migrations, seeding, and type-safe queries are all first-class. Use Prisma Studio and generated types aggressively.
The Outsider

From the outside, the most alarming observation is this: nobody in this conversation has confirmed the portal actually works right now.

The 4 Mongoose model files are deleted. Do all 4 routes still compile and run? Are there any stale imports pointing at those deleted files? If the answer is "I think so," that's not good enough for a live student portal where applications may be in flight.

Second concern: if src/lib/prisma.ts or src/config/dbconnect.ts ever gets imported by a frontend component (even accidentally), your DATABASE_URL and JWT secrets end up in the browser bundle. That's a live credential exposure vector.

Before any cleanup: run the server, hit /health, submit a test application, log in as admin. Verify the system works. Then clean up.

The Executor

Safe to do right now (zero risk):

  1. Run: npm uninstall styled-components exceljs @sanity/client @sanity/image-url vite-plugin-pwa lovable-tagger
  2. Run: npm uninstall --save-dev @types/axios @types/dotenv
  3. Run: git rm --cached .env and add .env to .gitignore

Needs careful execution (but do it):

  1. Move all backend files from src/ to server/: app.ts, config/, routes/, utils/, types/, lib/prisma.ts
  2. Update all relative imports in the moved files
  3. Update package.json scripts: src/app.ts → server/app.ts

Do NOT do: npm workspace split (too much risk on live portal right now).
